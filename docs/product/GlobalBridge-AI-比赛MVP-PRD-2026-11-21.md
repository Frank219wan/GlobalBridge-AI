# GlobalBridge AI 比赛 MVP 产品需求文档

**版本 v1.0｜2026 年 11 月 21 日｜适用对象：产品、设计、开发、测试及比赛演示团队**

## 1 产品目标与交付边界

GlobalBridge AI 是面向中国中小企业的 AI 出海业务助手。参赛版本帮助一家制造企业录入产品、了解目标市场、找到有公开依据的海外潜在客户，并将一封询盘转为可编辑的商务回复和报价草稿。演示结束后，用户可从 Dashboard 找回保存的业务记录。

## 2 用户与核心场景

【原文】主要用户是希望开拓海外市场的中国中小企业、缺少专业外贸团队的制造商与供应商，以及负责寻找经销商、进口商、采购商和处理询盘的业务人员（§二）。他们需要判断一家海外企业是否值得跟进，从外语邮件识别客户明确提出的要求，并减少从询盘到回复和报价的重复录入。

- **市场开发。** 业务人员选中已录入的智能家居传感器，调研德国市场并筛选潜在经销商或进口商，查看推荐理由和公开来源。
- **询盘处理。** 收到邮件后，业务人员粘贴正文，核对提取结果和待确认项，生成德文或英文回复，编辑并复制。
- **报价与回查。** 业务人员复用产品规格、已确认数量和单价，计算并保存报价草稿，随后从 Dashboard 重新打开客户、询盘、市场分析与报价。
- **比赛主线。** 【原文】深圳智能家居传感器制造商开拓德国市场（§五）。【建议】预备一份标注「演示样本」的脱敏或合成询盘，一家经真实搜索发现并核实公开资料的候选企业，以及自有演示产品规格和价格。若样本与真实企业关联，明确提示询盘为虚构情景，避免让观众误认为对方真实询价。

### 4.1 主流程与业务规则

1. **登录并建立资料。** 在 Demo 工作区创建企业和产品。后续页面传递产品和客户标识，通过后台读取资料，并展示本步实际使用的规格与价格。
2. **选择德国并启动调研。** 同轮请求可并行调用官方知乎搜索与海外检索。市场分析显示「知乎内容」「海外公开信息」「AI 推断」及来源链接。无依据的需求规模、增长率和竞争结论显示为资料不足。知乎观点可作背景，德国当地市场结论需独立的海外公开依据。
3. **匹配并保存客户。** 以业务类别和产品渠道是否一致为主，结合国家、客户类型以及官网证据。运营官网、产品页、经销业务页、法律声明或登记信息可作为核验依据。国家和主营业务分别核实，缺项显示「待核实」。打开原文链接，回到同一结果或详情。用户主动保存后进入客户列表。
4. **分析询盘。** 结果中六项字段各有值、状态和可定位文本证据。数量保留原句、数字及单位。日期含糊、规格相冲突、关键条件缺失时提示人工确认，并给出可用于回复的追问。保存后以用户修订值驱动邮件与报价。处理失败时可保留正文并重试。
5. **生成回复。** 用真实产品资料和最新确认的询盘数据生成主题与正文。缺失价格、交期、付款条件或认证，生成澄清问题或待确认措辞。用户改稿、复核后复制。邮件和报价均需用户确认后使用。
6. **生成报价并回查。** 建议 MVP 支持单行产品报价。数量取用户确认的询盘值，单价和币种取产品资料或用户输入，贸易条件由用户确认。总价由系统以十进制定点运算得出。采用 USD/EUR 及保留两位小数作为建议值，精度和舍入规则在 D2 锁定。币种变更要求重新确认单价，缺项时金额显示待补全，税费、运费和汇率仅按未来确认的规则处理。保存后从 Dashboard 重开，再用另一端登录同一工作区核验记录。

【建议】显示处理中、空结果、部分成功、超时和服务不可用。进行中的同一操作禁用重复提交，保存失败保留用户输入并允许重试。重试同一次保存应返回已生成记录或补足未完成写入。用户跨页退出有未保存编辑时提醒。搜索结果注明实时、历史或演示样本，并展示实际检索时间。

## 5 数据实体与保存策略

### 5.1 业务实体与关系

| 实体 | 核心字段 | 建议写入时机与规则 |
| --- | --- | --- |
| Demo 账号与工作区 | 账号标识、工作区标识、状态、到期时间 | 后台预置，业务读取和写入按服务端会话校验工作区。 |
| 企业与产品 | 企业简介、产品名称、简介、型号、规格、计价单位、金额、币种、更新时间 | 表单校验后保存。企业对产品为一对多。 |
| 市场分析 | 产品及查询快照、目标国家、需求与竞争及机会结论、状态、检索时间、来源关联 | 用户保存可回查的分析。只保存获准留存的引用及摘要。 |
| 来源证据 | 来源类型、许可状态、原链接、标题、作者在可取得时、访问时间、证据字段 | 市场分析或客户记录引用。第三方字段留存取决于服务与原站使用条件。 |
| 潜在客户 | 企业名称、标准化官网域、国家、主营业务、核实状态、匹配理由、产品与来源关联 | 用户选中并保存，按工作区去重。资料不足可用待核实状态保存。 |
| 询盘 | 客户、产品、确认后采购字段、缺失项、风险、追问、输入语言、分析时间 | 保存脱敏后正文或脱敏证据片段及结构化记录。原文留存条件见待决事项。 |
| 邮件草稿 | 对应询盘、语言、主题、正文、版本及更新时间 | 建议在会话内提供编辑与复制。持久化邮件若获确认，由用户主动保存。 |
| 报价 | 企业、客户、询盘、产品与快照、数量、单位、单价、币种、总价、贸易条件、状态及版本 | 用事务保存金额和快照。产品后续改价用于新建报价，已保存版本保留快照。 |

【建议】数据库对报价、询盘和客户的关系设置约束。归档已被引用的产品保留历史关联。双端同时保存时按记录版本检查冲突，用户重新加载后确认更新。日志记录耗时、结果状态及用量，业务正文和密钥排除在日志外。赛前维护一份最小演示数据备份，建议赛后七天清理演示工作区，实际期限由团队确认。

### 5.2 方案比较与选择

| 方案 | 交付收益 | 成本与条件 | 建议 |
| --- | --- | --- | --- |
| 统一后端 + 托管 PostgreSQL | Web 与桌面实时共享业务记录，事务、外键和金额精度容易统一，便于备份恢复。 | 需要数据库实例、部署网络和用量预算。数据库与应用的可达性及备份能力需提前实测。 | 首选。在 D2 前验证后端可读写及备份恢复。 |
| 单实例后端 + 持久卷 SQLite | 两端经同一 API 读写，部署和运维较少，适合低并发演示。 | 要求单实例与持久磁盘，确认写锁和重启恢复。后续扩容需迁移。 | 托管库未就绪时的备选。 |
| Web 本地存储 + 桌面本地库 | 单端可独立保留草稿。 | 历史分散，双端对齐需要同步、冲突处理和恢复逻辑。 | 两周 Demo 优先保证共享记录，本方案延后。 |

PostgreSQL 对金额可采用精确的 numeric。SQLite 适用性取决于单主机文件访问及并发写入模式。数据保存的技术选择与第三方内容留存许可分别确认。未获许可时只保留业务自填字段及独立核实且可保留的公开来源，与受限的供应商响应分开处理。[PostgreSQL 数值类型](https://www.postgresql.org/docs/current/datatype-numeric.html) · [SQLite 适用场景](https://sqlite.org/whentouse.html)

## 6 推荐技术架构与模块依赖

【建议】Web 浏览器与 Windows wrapper 访问同一 HTTPS 域名。一个应用实例交付 Web 页面和业务接口，后端统一鉴权、执行业务规则、写库并调用外部服务。以比赛现场和部署服务器的实际网络连通性决定部署地域。

| 层级 | 推荐选型与理由 |
| --- | --- |
| Web 与业务接口 | Next.js App Router + TypeScript + Node.js 24 LTS。Route Handlers 可承载同域业务接口，单个 Node.js 服务即可部署，减少跨端和跨服务联调。版本在 D2 按团队熟悉度和依赖兼容性锁定。[Next.js 路由处理](https://nextjs.org/docs/app/getting-started/route-handlers) · [部署说明](https://nextjs.org/docs/app/getting-started/deploying) · [Node.js 支持周期](https://nodejs.org/en/about/previous-releases) |
| Windows wrapper | 首选 .NET 10 LTS WinForms + WebView2 Evergreen。封装同址 Web，窗口内只加载受信任业务域，引用来源交给默认浏览器打开。禁用无需使用的原生桥接。安装时检测 WebView2，预备官方离线运行时安装包，并测试目标环境的签名和安装限制。交付 Windows 版本与架构由 D2 确认。[WebView2 文档](https://learn.microsoft.com/en-us/microsoft-edge/webview2/landing/) · [运行时分发](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution) · [安全建议](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/security) · [.NET 支持周期](https://learn.microsoft.com/en-us/dotnet/core/releases-and-support) |
| 会话与访问 | 预设账号，服务端保存密码哈希。会话使用安全 Cookie，写入操作校验来源和工作区。两端同账号各自登录。若向评委开放独立试用，预设独立工作区或限时账号，以免互相覆盖。 |
| 存储 | 统一关系库，首选托管 PostgreSQL，单实例 SQLite 作备选。当前文本优先的 P0 使用关系库即可，文件解析需要的对象存储随 P1 立项。 |

### 7.3 D1 至 D2 选型验证

下列门槛均为【建议】。由接入负责人保留脱敏的请求结果、可点击证据、错误类别、响应耗时和实际计费记录。

| 检查项 | 验收办法及决策 |
| --- | --- |
| 资格、地域与现场连通 | 在拟用部署服务器跑真实请求，确认账户、凭证、有效期、额度及并发限制。从演示网络分别打开 Web 与 Windows。鉴权错误修复账号、密钥或时间偏差后复测。 |
| 知乎相关性 | 使用三个演示主题各调用一次，至少两个主题返回可打开的相关原文来源，保留一次真实请求的时间、状态与证据。若首选接口无法满足，验证官方备选。 |

选择顺序为**真实可接入及使用条件 → 可核实企业覆盖 → 稳定性 → 总成本**。D2 至少锁定一个真实 Zhihu 接口、一个真实海外企业搜索方案及可切换备选。接口短时故障可呈现显式标注的已授权历史资料或演示样本，评审验收仍需真实调用证据。
